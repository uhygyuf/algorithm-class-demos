📄 Key points & why it is O(1)

1push(v): check full, then arr[++top]=v, minArr[top]=min(minArr[top-1],v)
2pop(): check empty, then clear both arrays at top and top--
3peek(): read arr[top], change nothing
4getMin(): read minArr[top] → O(1)
The courseware trace (reproduced): push(5) → [5] min 5; push(3) → [5,3] min 3; push(7) → [5,3,7] min 3; getMin() → 3; pop() → removes 7, min stays 3.
Why is getMin O(1)? minArr[i] holds the minimum of arr[0..i].
· push: a new value can only be smaller than the running minimum or not affect it, so min(oldMin, v) is the new prefix minimum;
· pop: both arrays retreat by one, and minArr[top-1] is already the minimum of what remains — nothing to recompute.
That is what makes it faster than scanning (O(n)) on every getMin: O(n) extra space buys an O(1) query.

Edges (as the exercise asks): push on a full stack → Stack Overflow!; pop on empty → Stack Underflow!; peek / getMin on empty → Stack is empty!.
Common mistakes: (1) top must start at -1 (not 0), otherwise the first element is off by one; (2) popping must clear both arrays, or a later push reusing that slot reads a stale minimum; (3) the first element has no previous minArr entry — handle it separately (the code here uses top==0 ? val : ...).
